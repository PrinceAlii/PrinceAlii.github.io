## Design Specificity Verdict

The site feels authored for Ali’s platform-engineering record, not category-interchangeable. The visual language is specific: warm graphite, oxidised-red signal, Schibsted Grotesk/Source Serif 4 pairing, asymmetrical columns, ruled records, and evidence-led copy.

The main weakness is evidence placement rather than visual direction. The homepage and project introductions spend substantial space establishing tone before showing concrete proof. That creates a measured catalogue experience, but asks a recruiter to do more navigation and scrolling than necessary.

### Deterministic and browser evidence

- Detector command: `node .../detect.mjs --json src/pages src/components src/layouts`
- Result: `[]`; zero findings, zero advisory findings, no rule names, no file locations.
- All public routes rendered with the expected status and one `h1`: `/`, `/projects`, both project details, `/experience`, `/contact`, `/404`, and `/writing`.
- No viewport-level horizontal overflow at 1440px, 390px, or 320px.
- Every route has `main#main-content[tabindex="-1"]` and a working `Skip to content` link; first Tab focused the skip link and activating it focused `main`.

- The only measured sub-44px interactive targets were project title links on `/projects`: approximately 263.4×35.5px and 295.1×35.5px at 390px, and 263.4×35.5px at 320px.
- Normal routes produced no browser warnings, errors, or page exceptions. `/404` emitted the expected 404 resource error. `/writing` emitted the expected empty-collection warning.

## Overall Impression

This is a strong, unusually coherent portfolio system. It looks and reads like a technical exhibition catalogue, and the strongest experience and project copy earns credibility through operational detail. The single biggest opportunity is to bring one decisive proof point closer to the homepage entry point, then give project pages a clearer conversational ending.

## What’s Working

1. The graphite field, calcium type, sparse red signal, fine rules, and serif reading voice create a recognizable visual system that is specific to this portfolio.

2. Concrete language such as Coder Cloud Development Environment, EKS, Artifactory, rate limits, and browser failures feels materially lived-in rather than generic résumé copy.

3. Responsive recomposition is thoughtful. At 390px and 320px the site becomes a readable single-column record without viewport overflow, while preserving the same hierarchy and semantic order.

## Priority Issues

### [P1] Concrete project evidence is missing from the homepage gateway

**Why it matters:** The first viewport contains the name, ABS role, a repeated ABS standfirst, resume, and contact. Projects are available only through the global navigation, so the strongest technical proof is one decision away from the primary entry point.

**Fix:** Keep the current restrained hero and do not restore the removed feature band. Use the standfirst or one understated link for a verified technical proof point or selected-work path before Work history.

**Suggested command:** `$impeccable clarify` or `$impeccable layout`

### [P1] Project case-study proof starts too late

**Why it matters:** On both project detail pages, the first viewport is dominated by title and description before “Built with,” “Problem,” or the case-study actions. The whitespace delays the evidence that earns trust.

**Fix:** Tighten the project-specific intro or pull the existing metadata/first section upward so one decisive proof point appears before the first scroll, while preserving the quiet field and asymmetry.

**Suggested command:** `$impeccable layout`

### [P2] Mobile project title links are smaller than the site’s 44px target

**Why it matters:** At 390px and 320px, project title links measure about 35.5px high. They are usable, but they are less forgiving for touch users and inconsistent with the shared 44px interaction rule.

**Fix:** Give the project title anchor a minimum 44px line box or hit area without changing the ruled-record topology.

**Suggested command:** `$impeccable adapt` or `$impeccable polish`

### [P2] `/experience` is credible but slow to scan

**Why it matters:** The current role begins with three dense paragraphs and six slash-separated areas of work. The page works for close reading but is less efficient for a recruiter verifying scope across five roles.

**Fix:** Add a concise static scan layer before the longer record copy. Keep the ruled entries and avoid cards, skill bars, or decorative summaries.

**Suggested command:** `$impeccable distill` or `$impeccable layout`

### [P2] Case studies end without a conversation path

**Why it matters:** The technical sections peak at “Outcome,” then drop directly into the footer. Visitors interested in discussing the work must reconstruct the next route themselves.

**Fix:** Add understated text links after “Outcome,” such as “Back to projects” and “Discuss this work,” using the existing underline/link treatment.

**Suggested command:** `$impeccable layout` or `$impeccable clarify`

## Persona Red Flags

- **Time-pressed recruiter:** The homepage does not expose a selected project or concrete technical proof point. They must navigate to Projects, then scroll past the project introduction before reaching evidence.

- **Technical peer or collaborator:** Reward Seat Finder exposes a live tool but no source link. If the implementation is intentionally private, the case study should say so; otherwise the verification path feels incomplete. Both project pages also lack a direct discussion/contact action at the end.

- **Mobile recruiter:** At 320px, the header reflows Contact onto a third navigation line. There is no overflow, but the extra row makes the navigation feel less stable on the narrowest supported width.
